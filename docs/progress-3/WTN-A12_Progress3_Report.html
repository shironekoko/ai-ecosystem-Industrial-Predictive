1. Dataflow and Ecosystem Design

โจทย์: ดอกกัด CNC สึกหรอสะสมจนต้องเปลี่ยน ถ้าเปลี่ยนเร็วเกินไปจะทิ้งอายุดอกและหยุดเครื่องบ่อย ถ้าเปลี่ยนช้าเกินไป ผิวงานจะเสียหรือดอกแตก ระบบจึงต้องบอก “อายุใช้งานที่เหลือ (RUL)” ระหว่างผลิต โดยใช้ข้อมูลที่เครื่องบันทึกเองเท่านั้น ไม่ต้องหยุดเครื่องวัดรอยสึก VB ระบบนิเวศประกอบด้วย AI 2 ตัว: (1) Time-series RUL service พยากรณ์จากสัญญาณแรง/แรงบิดทุกแนวตัดแบบเวลาจริง (2) Vision service จำแนกสภาพคมตัดจากภาพหน้าคมมีด (SHARP/USED/DULLED) ใช้ยืนยันเมื่อหยุดเครื่องหรือถอดดอก และเป็นแหล่ง label ของการ retrain ในอนาคต

รูปที่ 1 Ecosystem: Time-series RUL service ทำงานแบบเวลาจริง (แถวบน) · ที่เก็บข้อมูลและโมเดล (MinIO เป็น model registry) · Vision service อยู่ระหว่างรวมระบบ · วงจร MLOps/retrain (แถวล่าง, แผน)

1.1 Dataflow ของเส้นทางออนไลน์ (Time-series RUL)

#ขั้นตอนข้อมูล / การประมวลผลความถี่ / ขนาดComponent → ปลายทาง
1รับสัญญาณFx, Fy, Fz (dynamometer) + แรงบิด spindle, แรง/แรงบิดมอเตอร์แกน X/Y, ตำแหน่ง (controller) ของ 1 แนวตัด25 kHz + 500 Hz · ≈4.4 s/แนวStream Gateway (.h5 จริง)
2สัญญาณสดย่อเป็น 500 Hz, ≤ 50 จุด/สัญญาณ/เฟรม ส่งเฉพาะเครื่องที่ผู้ใช้เปิดดู10 เฟรม/วินาทีWebSocket → Machine Monitoring
3ฟีเจอร์รายแนวค่าเฉลี่ยในช่วงตัดเสถียร (y 5–90 mm) 7 ค่า → causal Hampel filter (ดูอดีตเท่านั้น) → % เปลี่ยนจากค่าตั้งต้นของดอก (29 แนวแรกหลัง break-in) + เวลาตัดสะสม + เครื่อง + ตำแหน่งแนวตัด1 เวกเตอร์ 12 ค่า/แนวruntime (โค้ดเดียวกับตอนฝึก)
4พยากรณ์หน้าต่าง 29 แนวล่าสุด (= 1 ชั้นงาน = 1 คาบฤดูกาล) → GRU ensemble 5 ตัว → เวลาถึง VB 103 / 140 µm → ข้อจำกัดฟิสิกส์ TEOL คงที่ → RUL, P10–P90, สถานะ, คำแนะนำ~1.6 ms/แนว (numpy)WebSocket + REST → Dashboard
5การตัดสินใจคำแนะนำยกระดับ → alarm (INFO/WARNING/CRITICAL); REPLACE_NOW → interlock หยุดป้อน รอผู้ควบคุม “ถอดดอก/ตัดต่อ” → บันทึก auditตามเหตุการณ์PostgreSQL (alarms, audit)
6หลังถอดดอกเปิดเผย VB จริง (วัดหลังถอดดอก) → เทียบสิ่งที่ระบบบอกระหว่างใช้งาน: MAE, เวลาที่สั่งเปลี่ยนเทียบหมดอายุจริง → label สำหรับ retrain1 ครั้ง/ดอกReports, JSONL → (แผน) MinIO datasets
7วงจรชีวิตโมเดลฝึกออฟไลน์ → npz (น้ำหนัก + เวกเตอร์ทดสอบตัวเอง) + json (อินพุต, เกณฑ์, ดอกฝึก/ดอกสงวน, ช่วงความเชื่อมั่น, sha256) → MinIO → backend ตรวจ sha256 + self-test ก่อนใช้114 KB/เวอร์ชันMinIO models/tool-rul/

1.2 หลักการออกแบบ

  • อินพุตที่โรงงานมีจริง: ไม่ใช้ VB เป็นอินพุต (ต้องถอดดอกไปส่องกล้อง) VB ใช้เป็น label ตอนฝึกเท่านั้น
  • Causal ทั้งเส้นทาง + โค้ดเดียวกัน: ตัวกรอง outlier, ฟีเจอร์ และข้อจำกัดฟิสิกส์ใช้เฉพาะข้อมูลอดีต ไฟล์ runtime.py ใน backend ตรงกับที่ใช้สร้างชุดฝึก (มี test บังคับ)
  • ไม่สปอยข้อมูล: ดอกที่สตรีมไม่เคยใช้ฝึก ไม่ส่ง VB, RUL จริง หรือชื่อไฟล์ไปหน้าเว็บจนกว่าจะถอดดอก
  • Model registry บน MinIO: แยกเวอร์ชัน มี latest.json สลับ/ย้อนเวอร์ชันได้ ไม่มีโมเดลสำรองหรือค่าสมมุติ ถ้าโหลดไม่ได้จะแจ้งว่าไม่พร้อม
  • Human-in-the-loop: AI เป็นผู้แนะนำ คนตัดสินใจ (interlock + audit) และ vision ใช้ยืนยันสภาพคมตัด
  • Modular: backend แบ่งตาม feature ใน docker compose (FastAPI, React, MinIO, PostgreSQL, Redis/ARQ, MLflow) จึงเพิ่ม vision/retrain worker ได้โดยไม่กระทบ service เดิม

2.3 แบบจำลอง ตัวแปร และการควบคุมการทดลอง

  • Time-series (3 แบบ): Fleet reference = อายุเฉลี่ยของเครื่อง − เวลาตัด (baseline) · StateSpace = VB แฝง + Gamma increments + particle filter 4,000 อนุภาค → เวลาข้ามเกณฑ์ (ทางอ้อม) · GRU direct-RUL = GRU 1 ชั้น hidden 32 อ่านหน้าต่าง 29 แนว × 12 ฟีเจอร์ → softplus 2 หัว, loss L1, Adam 30 epochs, ensemble 3 ตัว (production 5 ตัว)
  • ตัวแปรต้นที่ทดสอบ: รูปแบบ GRU 4 แบบ (direct / +noise σ=1 / ปรับแก้อายุอ้างอิง / ทั้งคู่) เลือกแบบ nested LOTO บนดอกฝึก 6 ดอกเท่านั้น · ablation อินพุต (เวลา+เครื่อง / เซนเซอร์+เวลา / ครบ) · ข้อจำกัดฟิสิกส์เปิด/ปิด · การจัดการ outlier (causal / STL / ไม่จัดการ)
  • ควบคุม: seed คงที่, normalization และช่วงความเชื่อมั่นคำนวณจากดอกฝึกเท่านั้น, เงื่อนไขการตัดเดียวกันทุกดอก
  • Vision: YOLOv8n-cls (transfer learning จาก ImageNet) 224×224, augmentation (flip, หมุน ±10°, scale ±10%, HSV), AdamW + weight decay 5e-4, cosine LR + warmup 2 epochs, AMP, 20 epochs, บันทึกผลใน MLflow

2.4 ตัวชี้วัด

RUL (นาทีของเวลาตัด): MAE / RMSE / Bias ทั้งอายุและช่วง 20% ท้าย · %late = สัดส่วนแนวที่พยากรณ์อายุเกินจริง > 1 ชั้นงาน (2.73 นาที) ซึ่งเป็นความเสี่ยงหลัก · accuracy / macro-F1 ของสถานะ · decision replay (เวลาที่สั่ง REPLACE_NOW เทียบหมดอายุจริง, % อายุดอกที่ใช้, เวลาที่แจ้งวางแผนล่วงหน้า) · ความครอบคลุมของ P10–P90 · Wilcoxon รายดอก Vision: top-1, macro-F1, precision/recall รายคลาส, latency · ระบบ: ความคลาดของจังหวะสตรีม (วินาที/แนว), parity ระหว่าง backend กับออฟไลน์, pytest

2.6 การทดลองระยะถัดไป

  1. รวม Vision เข้าระบบ: ย้ายโมเดล YOLOv8 ขึ้น MinIO/registry แบบเดียวกับ RUL, ต่อ vision worker กับหน้า Tool Image Wear และวัด end-to-end latency/accuracy บนภาพที่อัปโหลดจริง
  2. Retrain pipeline แผน: trigger เมื่อมีดอกที่ถอดแล้ว ≥ N ดอก (label จาก VB หรือภาพที่วิศวกรยืนยัน) → ARQ GPU worker ฝึกใหม่ → gate = LOTO MAE ไม่แย่กว่าเวอร์ชันเดิม และ %late = 0 → shadow mode คู่กับเวอร์ชันเดิม → publish (MinIO + MLflow) → สลับ latest.json
  3. ทดสอบความทนทาน: เครื่องใหม่ (few-shot calibration), drift ของสัญญาณ และเกณฑ์นโยบาย P10 ที่ต่างกัน (ต้นทุนดอก vs ความเสี่ยงงานเสีย)
